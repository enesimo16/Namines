# Namines — Relationships, Dependencies, Blocking Chains

These are explicit dependency / blocking / supersession / part-of relationships documented across the phase docs and CHECKLIST gates. Each line names two or more entities and the nature of the relationship between them.

- **Doc 27-LIFECYCLE-PIVOT.md supersedes the priority ordering** of docs 00-VISION.md, 01-MARKET.md, 02-PRODUCT-SCOPE.md, and 24-ROADMAP.md — it changes their sequencing, not their underlying content.
- **Doc 30-SERVER-SIDE-BRANCHING.md is an explicit precondition for doc 29-DATABASE-CHANGE-REVIEW.md** — stated directly in the docs: "30, 29'un ön koşuludur" (30 is a precondition of 29) — the Change Review UI cannot work meaningfully without server-side branching existing first.
- **Gate G7 (migrating the control DB from SQLite to PostgreSQL) is a precondition for gate G10** (adding server-side `branches`/`schema_versions` tables) — documented as "Postgres olmadan gerçek anlamda yapılamazdı" (couldn't really be done without Postgres).
- **Doc 28-IMPACT-ANALYSIS-ENGINE.md's Layer 6 (affected API/UI detection) is explicitly deferred to depend on the Gateway existing** — gate G8.7 shipped only a cheap static-scan proxy for this layer, not the full version.
- **`FkCascadeAnalyzer` (built at gate G3) was directly reused and generalized — not rewritten — into `SchemaImpactAnalyzer` (gate G8).**
- **Namines Desk requires connection-string encryption to exist before it can store live-DB credentials** — the backend explicitly refuses to save an unencrypted connection if `Security__ConnectionEncryptionKey` is not configured (fails closed, not silently).
- **"Push schema changes directly to the live database" (planned in `namines_desk/05-DEPLOYMENTS.md` §4.3) is explicitly blocked until Namines Vault exists** — because `ALTER TABLE`/`DROP COLUMN` is irreversible without a pre-migration backup, and Vault is the only planned component that provides that backup.
- **Desk's planned GitHub-push deployment feature (`05-DEPLOYMENTS.md` §4.4) is blocked on GitHub App credentials** — the same blocking dependency that stalls Namines Bot from ever writing to a pull request.
- **Redis is a soft dependency gate, not a hard code-blocking one.** The SignalR backplane and `RedisPresenceStore` were already written at gate G6 and activate via a single `.env` line; only `GatewayRateLimiter`'s internal body needs rewriting (~1 hour of work) once Redis is actually adopted. Redis gates: multi-instance rate-limit correctness, the Gateway's metadata cache, and GraphQL support (explicitly marked in second-phase doc "kalan büyük işler" item #2 as blocked on the Redis adoption decision).
- **The MCP server's `namines_open_change_request` tool is the only MCP tool that writes anywhere, and it writes to the Namines server (opening a review) — never to the user's own database.** A deliberate architectural firewall (doc 33 §7).
- **NSL model expansion follows a hard prerequisite chain**: `identity` support (gate G42) → enum support (gate G44, which also surfaced a Turkish-culture `ToUpper()` bug) → `generated`/`collation`/array column types (gate G45) → canonical JSON IR `ir.json` (gate G46). Each addition is described as "the later it's added, the more expensive," because every DDL generator built on top of the model raises the cost of retrofitting it.
- **Testcontainers vs. `Namines.Tests.RunTests` isolation**: gate G12 discovered that Testcontainers 4.x's `Docker.DotNet.Enhanced` fork shares a compiled DLL filename with the project's own `Docker.DotNet` 3.125.15 dependency (used by `DockerBackupService`), causing silent wrong-DLL resolution that broke `DockerBackupService.cs` at compile time whenever both were loaded in the same process. Resolved by **never introducing Testcontainers into the runtime path** — instead reusing the already-proven `Docker.DotNet` client (via `BranchTestRunnerService`) inside a completely separate test project.
- **second-phase doc 12 (Supabase integration) depended on second-phase doc 11's `SqlDdlSchemaParser`** — described as the "missing link" that made the entire Supabase migration-reading chain work without needing any new Supabase-specific API integration.
- **second-phase doc 09 (schema alternatives A/B comparison) deliberately reuses the existing `SchemaImpactAnalyzer`/diff engine** instead of building new multi-canvas infrastructure from scratch — an explicit "cheaper reuse over new subsystem" engineering decision.
- **NAI model naming (`nai-flash` / `nai` / `nai-pro`) abstracts the underlying AI provider models** specifically because a previously-configured Groq model once started returning "model does not exist," which broke schema generation product-wide. This single incident directly motivated the abstraction layer described in doc 36-KOTA-VE-AJAN.md.
- **Gate G39 ("app doesn't start" bug found despite 857 green tests) is the origin of a recurring project-wide lesson**: "tests passing proves nothing" about whether the app actually boots — cited repeatedly afterward as a reason live/manual verification is treated as mandatory, not optional, alongside automated tests.
